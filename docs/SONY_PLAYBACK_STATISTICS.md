# Sony 播放统计口径与查询

Sony 从本机播放会话生成统计，iOS 和 Android Controller 继续消费现有统计响应。统计结果按会话开始时间归入请求范围，使用左闭右开的时间区间。有效播放次数沿用监控器现有的 30 秒或歌曲时长一半门槛。

## 统计口径

| 指标 | 计算规则 |
|---|---|
| 收听时长 | 范围内所有会话的 listenedMs 合计，包含进行中的会话 |
| 有效播放次数 | 范围内 countedPlay 为真的会话数 |
| 歌曲数 | 范围内不同 trackKey 的数量 |
| 完播次数 | 已结束会话中 completed 为真的数量 |
| 跳过次数 | 已结束会话中 skipped 为真的数量 |
| 完播率 | 完播次数除以已结束会话数 |
| 跳过率 | 跳过次数除以已结束会话数 |

endedAt 非空表示会话已结束。进行中的会话不进入结果率的分子和分母，即使旧数据携带了结果标记也如此。没有已结束会话时两项比率返回 0，保持现有数值字段契约。一条有效播放和两条快速跳过形成三个已结束会话时，跳过率返回 2/3；客户端仍按其现有百分比格式展示。

缺少曲目元数据的会话保留在总量、歌曲排行和歌手排行中。曲目展示字段使用空字符串或空封面，歌手缺失或全部为空白字符时归入未知歌手。已有非空歌手名称保留原文。排行先按收听时长、有效播放次数降序，再按歌曲键或歌手名称稳定排序，最多返回十项。

## 数据库读取

PlaybackStatsCalculator 在一个 Room 事务内调用五个聚合查询入口，最多执行五次读表 SELECT：

1. 总收听时长、有效播放次数、不同歌曲数、结束会话数及结果计数。
2. 会话与曲目元数据 LEFT JOIN 后的歌曲前十名。
3. 同一元数据快照下的歌手前十名。
4. 每个有记录的 UTC 日桶中的最早和最晚开始时间。
5. 本地自然日范围与会话表连接后的每日聚合。

空历史的第五次查询为不读表的空结果常量 SELECT。查询不逐条读取曲目，也不将全部 PlaySessionEntity 实例化后分组。返回数据随有记录的日期数量和固定大小的排行榜增长；SQLite 仍需扫描或聚合范围内会话，因此不宣称总执行时间与会话数量无关。数据库表结构与版本保持原样，时间范围条件沿用现有 startedAt 索引。

结果计数使用整数聚合；若异常历史数据使 SQLite 整数 SUM 溢出，统计请求按已有错误路径失败，不转换为可能丢失精度的浮点总量或伪造成功数值。

## 日期和时区

每次汇总捕获并复制 TimeZone，沿用请求 Locale 的周起始日；日期标签采用公历和 Locale.US，避免泰历等地区日历改变协议日期标签。今日、本周、本月分别取自然日、自然周和自然月；ALL 继续使用从 epoch 0 到 Long.MAX_VALUE 的左闭右开区间。

日边界通过 Calendar 的日期运算构造，处理夏令时的 23、25、23.5 和 24.5 小时自然日，以及午夜缺失或重复。SQL 不依赖进程的 native localtime，也不使用固定时区偏移替代夏令时规则。

第四次查询只返回实际占用的 UTC 日桶。每桶实际最早和最晚记录相隔不足 24 小时，Java 只生成这些局部范围内的本地日边界，按开始时间去重并裁剪到原请求区间。第五次查询通过 VALUES CTE 连接这些范围。这样，即使两条记录相距极远，也不会枚举中间所有空白日期。VALUES 行数不受 compound SELECT 的 500 项限制，且内部生成的日边界不会消耗每行三个绑定参数；依据见 [SQLite SELECT 文档](https://www.sqlite.org/lang_select.html#the_values_clause)和[CTE 发布记录](https://www.sqlite.org/changes.html#version_3_8_3)。

## 验证要求

真实 Room 回归使用独立的内存参考算法核对完整结果，覆盖空记录、快速跳过、进行中会话、元数据缺失、Unicode 空白、排行并列、自然周期、夏令时、时区切换、极端时间和并发写入。QueryCallback 记录实际 SQL 与绑定值，验证查询预算；双 Room 连接验证总量、元数据和每日趋势来自同一个快照。

性能数据使用同一模拟器、同一数据和相同回调配置，对比测试内保留的旧版 N+1 读取方式与新聚合路径。分别记录 1000、10000、100000 条数据的查询数量及耗时。少量样本的 p95、Java 堆使用量端点差和模拟器时延均需保留测量口径，不视为 Sony 真机 p95 或峰值内存。

## 冒烟发现的既有问题与剩余验收

首轮完整冒烟未授蓝牙运行时权限，必选 8/8 通过，但可选 BLE Health Watchdog 失败。真实日志显示 Activity 正常拒绝缺权限启动后，调试恢复广播仍冷启动前台服务，`startForeground` 因 connectedDevice 权限前提不满足抛出 SecurityException。另一个工具问题是 `--no-debug-control` 尚未传给 watchdog 检查，因此该选项并未阻止它发送恢复广播。

上述服务、调试接收器、Manifest 和冒烟脚本均与基线 `2570913` 完全一致。本批只修改统计、测试和文档；这两项既有缺陷保留待修，首轮失败报告也保留，权限完整后的通过结果不表示缺权限路径已修复。

BLE 消息字段、数据库表结构和版本均未改变。本批没有 iOS 源码改动，因此未要求或运行 iOS quick/full smoke；工作区已有的 iOS 文案修改保持原样。Sony 真机上的历史量级性能、老系统兼容性以及与 iPhone/Controller 的统计展示仍需实机验收。
